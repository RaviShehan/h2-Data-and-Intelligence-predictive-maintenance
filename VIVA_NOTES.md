# H2 Data Intelligence Viva Notes

This document summarizes how to explain the H2 Data and Intelligence component during viva.

## 1. What is H2?

H2 is the Data and Intelligence part of the Group H Predictive Maintenance System.

Its responsibility is to receive machine sensor data, extract useful features, predict machine health risk, detect anomalies, and store prediction results.

## 2. What problem does this solve?

Machines can fail due to abnormal temperature, vibration, or operating conditions.

This system helps identify machine health risk early so that maintenance can be planned before serious failure happens.

## 3. Main System Flow

```text
Sensor Simulator
      ↓
Kafka Producer
      ↓
Kafka Topic
      ↓
Kafka Consumer
      ↓
FastAPI Prediction API
      ↓
Feature Extraction
      ↓
SciPy Signal Processing
      ↓
RandomForestClassifier Model
      ↓
Anomaly Detection
      ↓
PostgreSQL Database
```

## 4. Why Kafka is used

Kafka is used to simulate real-time streaming sensor data from machines.

In a real industrial system, machine sensors continuously send data. Kafka helps handle this streaming data flow.

## 5. Why FastAPI is used

FastAPI is used to expose prediction and monitoring endpoints.

Main API endpoints:

* `GET /`
* `POST /predict`
* `GET /predictions`
* `GET /model-info`
* `GET /model-evaluation`
* `GET /feature-importance`

FastAPI is lightweight, fast, and suitable for machine learning APIs.

## 6. What features are extracted?

From raw sensor readings, the system extracts vibration and signal-processing features.

Basic vibration features:

* vibration_total
* vibration_rms
* vibration_mean
* vibration_peak
* vibration_std

SciPy signal-processing features:

* signal_rms
* signal_mean
* signal_peak
* signal_std
* signal_skewness
* signal_kurtosis
* spectral_energy

These features help the model understand machine vibration behavior better.

## 7. Why SciPy is used

SciPy is used to extract statistical signal features such as skewness and kurtosis.

The system also uses FFT-based spectral energy to include frequency-domain information from vibration signals.

This improves the machine learning model because vibration patterns are important in predictive maintenance.

## 8. What dataset is used?

The system uses the NASA IMS Bearing Dataset.

This is a real predictive maintenance dataset containing vibration data from bearing experiments.

The raw dataset is stored locally in:

```text
data/raw/
```

This folder is ignored by Git because the dataset is large.

The processed dataset is:

```text
data/training_data_real.csv
```

## 9. What machine learning model is used?

The system uses a RandomForestClassifier.

The model predicts one of three machine health states:

* NORMAL
* WARNING
* CRITICAL

RandomForestClassifier was selected because it works well with tabular feature data and can provide feature importance values.

## 10. What is the model accuracy?

The current real NASA IMS model accuracy is:

```text
0.9645
```

This accuracy was achieved after adding SciPy-based statistical and frequency-domain signal features.

## 11. What is feature importance?

Feature importance explains which input features contributed most to the RandomForestClassifier prediction.

The feature importance report is generated by:

```text
models/feature_importance_real.py
```

The output file is:

```text
models/feature_importance_real.json
```

The API endpoint is:

```text
GET /feature-importance
```

This improves explainability because we can show which vibration or signal features are important to the model.

## 12. What is anomaly detection?

Anomaly detection checks whether sensor values are outside safe limits.

The system checks:

* very high temperature
* abnormal vibration level
* very low rpm
* very high rpm

This is useful because even if the ML model gives a prediction, the system can still warn about unsafe sensor behavior.

## 13. Why PostgreSQL is used

PostgreSQL is used to store prediction history.

Stored data includes:

* machine ID
* raw sensor data
* extracted features
* risk level
* failure probability
* recommended action
* anomaly result
* timestamp

This allows the system to keep historical prediction records.

This project is not just a simple prediction API. It includes real-time streaming simulation using Kafka, REST API prediction using FastAPI, real NASA IMS dataset based ML training, SciPy-based signal processing, anomaly detection, PostgreSQL storage, feature importance explainability, and automated tests.

## 16. Current limitations

Current limitations:

* Only one NASA IMS test set is used currently
* The dataset labels are assigned based on time progression
* The system is currently local and not deployed
* No dashboard is included in H2 because dashboard work belongs to another team component
